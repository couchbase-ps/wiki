About this review

This page is a checklist for one Couchbase database. You fill it in with the team. Tick the things you already do.

At the start you say where Couchbase runs:

  • Capella — Couchbase hosts the cluster.
  • Self-managed Server — you run Couchbase Server on your own machines.
  • Autonomous Operator — Couchbase runs on Kubernetes.

The checklist changes with that choice. A Capella review does not ask about Linux settings, because you do not manage those machines.

This page never logs into your cluster. It does not read data and it does not change settings. You answer from what the team knows.

When you finish, you save a report into the wiki page: what is missing, how serious it is, and what to do next. The page also keeps your answers, so you can open the review again from the editor and change it.

How to use it

Do these three steps in order. Your answers stay in this window until you click Save to Wiki. If you click Close before you save, you lose them.

Step 1. Open Review and fill in the names

  1. Click the Review tab at the top.
  2. In Customer name, type who the review is for. Example: Acme Retail.
  3. In Reviewer name, type your name.
  4. In Workload, type the application you are reviewing. Example: Orders API.
  5. Under Type, choose one option:
    • Capella if Couchbase hosts the cluster.
    • Self-managed Server if you run the machines.
    • Autonomous Operator if Couchbase runs on Kubernetes.

The page keeps this as you type. Questions that do not fit the type you chose are hidden.

Step 2. Tick what you already do

  1. On the left, click a pillar. A good place to start is Operational Excellence.
  2. Read the question.
  3. Look at Audience. It says who should answer: Platform, Application, or Security.
  4. Tick a box if you already do that thing.
  5. Leave a box empty if you do not do it. The report will list it as something to fix.
  6. If a box says Only if this applies, leave it empty when you do not use that feature. That empty box is not a problem.
  7. Use Notes when you want to explain a choice. Example: We have one site only.
  8. Click the next pillar on the left and do the same. You can skip one and come back.

Step 3. Get the report

  1. Click Submit Review.
  2. Read the summary. It shows how many questions you answered, and how many gaps are high, medium, and low.
  3. Click Save to Wiki. The report goes into the wiki page at the cursor.
  4. Save the wiki page.

To change the review later, open the page in the editor and click Edit Well-Architected Assessment Tool.

To review a different application, click Start New Review. That clears the answers in this window. It does not change your Couchbase cluster.

What the questions cover

There are six groups. The last one is Data Management and Consistency: durability, CAS, expiry, and what happens when two clusters both accept writes. Mobile and vector search are not part of this review.

Operational Excellence

Someone can see resident ratio, a failed rebalance, and a slow query before users report it. Upgrades swap one node at a time. On Linux you run yourself, swappiness is 1 and transparent huge pages are off.

Security

Each service has its own database user. The password is not in source control. The SDK connects with couchbases:// and checks the certificate. Administrators sign in through the company directory, not a shared local account.

Reliability

Production has at least three nodes, replicas, and copies in different racks or zones. Two server groups can add an arbiter in a third group so failover still has a majority. Backups have been restored once, not only scheduled.

Performance Efficiency

A document you already know by id is a key-value call. Frequent SQL++ uses an index that fits in the Index service memory. Capella uses Magma. On Server 8, Magma is the usual engine when the bucket is larger than memory. Couchstore still fits a bucket that stays in RAM.

Cost Optimization

You look at the access pattern before you add nodes. Development and test clusters on Capella are not left running all night.

Data Management and Consistency

Writes that must survive a node loss use a durability level the topology can meet. Concurrent updates use CAS. The XDCR conflict mode is chosen when the bucket is created, and every bucket in that replication uses the same mode.
